## Fusion in the store and service — 2026-10-09

- **Decision:** a Transcendent is a separate canonical record, not a new profile schema. `ProfileV1` and its codec are unchanged (so every existing hash, replay and projection stays valid). The store is schema 2: one added `fusions` table (host, donor, both species, both Uniques, operation, time); a schema-1 store is upgraded in place on open and a test proves its rows survive.
- `ProgressionStore.fuse(FuseRequest)` is one transaction: revisions of both profiles and the wallet, `FusionRules.check`, price debit, the fusion row, the host revision bump, and the operation record. A replay returns the first result and debits nothing more. The donor profile row stays (like a released Pokemon); `fusion(host)` and `consumedBy(donor)` read the record.
- `ProfileService.fuse(...)` checks ownership, craft lock and "not in a battle", resolves the Transcendent, commits, then removes the donor from party or PC (`PartyStore.remove` and `PCStore.remove`, confirmed present in Cobblemon 1.8.1 with javap) and projects the host. The login sweep finishes removing a donor whose removal was cut short.
- `ProfileService.snapshot` now gives a fused Pokemon its Transcendent in `AscensionBattles`, so a real fusion reaches the simulator. `itemRewardPercent` gives `AscensionRewards.scaleItemQuantity` the best bonus in the party (plain 777 = 20%, a 777 Transcendent = signature percent x benefit share).
- Store tests 5 added (success and exact replay, no second fusion, refused fusion changes nothing, crash before commit, schema-1 upgrade); everything builds and passes. **Not built:** the network request and confirmation, the fusion screen and hover, the Transcendent's display in the inspect screen. **Not seen live:** the donor removal, the battle snapshot, the loot scaling.

## P1 ranked domain foundation — 2026-10-05

Added in `domain/.../v1/`, beside the untouched schema-zero prototype (the `fabric` module still uses the prototype types and its build is unchanged):

- `ProfileV1` (schema 1): stable slot IDs (`prefix:N`/`suffix:N`), per-slot rank I–V, milestone ledger with `highestLevelObserved`, spent-credit invariant, optional `UniqueInstance`.
- `RankedRules` + `design/ranked-catalog.json`: five strictly increasing, non-overlapping bands per affix; one Unique definition (`ashen_heart`). **Bands are derived placeholders** (rank I = existing range, later bands span `ceil(rankIMax/2)`; `type_focus` matches the spec's Fire Focus example) and need balance approval. Combat caps were not revisited for rank V.
- `RankedProgression`: create (with milestone catch-up), `observeLevel`, `upgrade`, rank-preserving `reforge`/`refine`, `promote` (adds one rank-I slot), `installUnique`/`replaceUnique`, `eligibleUniques`. Refusals throw `CraftException` with a stable `Reason`.
- `ProfileV1Codec` (strict JSON projection) and `SchemaZeroMigration.importStored` (reads either form; re-running over schema-1 output is a no-op).

Not done in P1 (later packages): wallet/material balances and Catalyst assembly (P2), the transaction/operation-replay service and recording the migration operation ID (P2), lifecycle hooks (P3), simulator effects for ranks (P4+). Slot IDs and rolls are integer percent; conversion to basis points belongs to the battle snapshot.

Catalog expansion (2026-10-05): 12 more affixes (24 total: 12 prefix, 12 suffix). Four are rare powerhouses (`type_mastery` weight 8, `overwhelming_force` 3, `iron_resolve` 3, `type_bulwark` 8); the rest are standard (weight 100) or uncommon (30–40). Template weights were rescaled from 1 to 100 (same relative odds) so rare weights can be below standard. `type_mastery`/`type_bulwark` share a family with Type Focus/Type Ward, so they never coexist. Mastery rank V reaches 51–60%. Combat channel caps were raised from 25/15/15 to **100/50/50** (outgoing damage / incoming reduction / healing) so no single affix is clipped at rank V (a test enforces this); `Rules` now accepts caps up to 100 but rejects a reduction cap above 90. Cap values remain provisional until simulator testing, and stacking several affixes in one channel is still clamped. Existing schema-zero rolls are unaffected. `tools/analyze_balance.py` now validates the schema-1 example and expects 24 templates.

Verification: `:domain:test` 63 tests passing (21 prototype + 42 new covering the P1 rows of the acceptance matrix and the weighting), `:fabric:build` successful. No in-game verification.

## P2 canonical store — 2026-10-05

New Gradle module `store/` (pure Java + pinned `org.xerial:sqlite-jdbc:3.53.4.0`, no Minecraft imports; the `fabric` module does not use it yet) and `domain/.../v1/MaterialWallet`.

- `MaterialWallet`: all five materials, nonnegative, checked arithmetic, revisioned, all-or-nothing debits, Catalyst assembly.
- `ProgressionStore`: one SQLite file per world (WAL, `synchronous=FULL`, STRICT tables with CHECK/UNIQUE constraints). Tables: `meta`, `profiles`, `wallets`, `wallet_balances`, `operations`, `milestone_awards`, `migrations`. Every mutating call (`acquire`, `migrate`, `grant`, `assembleCatalyst`, `craft`) is one transaction that also records its result under the caller's operation ID: a repeated request returns the recorded snapshot, a reused ID with different parameters is rejected, refusals commit nothing.
- Guards: authority and content-version checks on open, `REQUIRE_EXISTING` mode so a missing store is never silently recreated, unknown schema/corrupt file refused and preserved, tampered rows preserved and block use (`STORED_DATA_INVALID`), stale profile/wallet revisions rejected, projection backlog (`projectionBacklog`/`markProjected`) for crash recovery, schema-zero `migrate` recording its operation ID and source digest (re-run is a no-op).
- Fault injection (`Faults`): crashes after validation, before commit and after commit are covered; reopening shows no change or a replayable committed result with no second debit or roll.

Verification: `:domain:test` 71 and `:store:test` 29 passing (100 total), `:fabric:build` successful; a mutation check (disabling replay) failed 11 store tests. No in-game verification.

Not done: wiring the store into `fabric` and replacing the prototype `PokemonProfiles`; the application service (ownership, battle/trade locks, preview tokens); SQLite native-library packaging inside the Fabric jar (jar-in-jar must be proven on a dedicated server); tables for acquisition intents, reward entitlements, encounter runs and pending presentations; consistent world+SQLite backup; catalyst threshold (100) is provisional.
