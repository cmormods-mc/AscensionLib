# Build status — 2026-10-03

This is the exact implementation and validation record for the first standalone foundation. The full design documents describe the intended finished product, not current behavior.

## P1 ranked domain foundation — 2026-10-05

Added in `domain/.../v1/`, beside the untouched schema-zero prototype (the `fabric` module still uses the prototype types and its build is unchanged):

- `ProfileV1` (schema 1): stable slot IDs (`prefix:N`/`suffix:N`), per-slot rank I–V, milestone ledger with `highestLevelObserved`, spent-credit invariant, optional `UniqueInstance`.
- `RankedRules` + `design/ranked-catalog.json`: five strictly increasing, non-overlapping bands per affix; one Unique definition (`ashen_heart`). **Bands are derived placeholders** (rank I = existing range, later bands span `ceil(rankIMax/2)`; `type_focus` matches the spec's Fire Focus example) and need balance approval. Combat caps were not revisited for rank V.
- `RankedProgression`: create (with milestone catch-up), `observeLevel`, `upgrade`, rank-preserving `reforge`/`refine`, `promote` (adds one rank-I slot), `installUnique`/`replaceUnique`, `eligibleUniques`. Refusals throw `CraftException` with a stable `Reason`.
- `ProfileV1Codec` (strict JSON projection) and `SchemaZeroMigration.importStored` (reads either form; re-running over schema-1 output is a no-op).

Not done in P1 (later packages): wallet/material balances and Catalyst assembly (P2), the transaction/operation-replay service and recording the migration operation ID (P2), lifecycle hooks (P3), simulator effects for ranks (P4+). Slot IDs and rolls are integer percent; conversion to basis points belongs to the battle snapshot.

Catalog expansion (2026-10-05): 12 more affixes (24 total: 12 prefix, 12 suffix). Four are rare powerhouses (`type_mastery` weight 8, `overwhelming_force` 3, `iron_resolve` 3, `type_bulwark` 8); the rest are standard (weight 100) or uncommon (30–40). Template weights were rescaled from 1 to 100 (same relative odds) so rare weights can be below standard. `type_mastery`/`type_bulwark` share a family with Type Focus/Type Ward, so they never coexist. Mastery rank V reaches 51–60%. Combat channel caps were raised from 25/15/15 to **100/50/50** (outgoing damage / incoming reduction / healing) so no single affix is clipped at rank V (a test enforces this); `Rules` now accepts caps up to 100 but rejects a reduction cap above 90. Cap values remain provisional until simulator testing, and stacking several affixes in one channel is still clamped. Existing schema-zero rolls are unaffected. `tools/analyze_balance.py` now validates the schema-1 example and expects 24 templates.

Verification: `:domain:test` 63 tests passing (21 prototype + 42 new covering the P1 rows of the acceptance matrix and the weighting), `:fabric:build` successful. No in-game verification.

## P2 canonical store — 2026-10-05

New Gradle module `store/` (pure Java + pinned `org.xerial:sqlite-jdbc:3.53.4.0`, no Minecraft imports; the `fabric` module does not use it yet) and `domain/.../v1/MaterialWallet`.

- `MaterialWallet`: all five materials, nonnegative, checked arithmetic, revisioned, all-or-nothing debits, Catalyst assembly.
- `ProgressionStore`: one SQLite file per world (WAL, `synchronous=FULL`, STRICT tables with CHECK/UNIQUE constraints). Tables: `meta`, `profiles`, `wallets`, `wallet_balances`, `operations`, `milestone_awards`, `migrations`. Every mutating call (`acquire`, `migrate`, `grant`, `assembleCatalyst`, `craft`) is one transaction that also records its result under the caller's operation ID: a repeated request returns the recorded snapshot, a reused ID with different parameters is rejected, refusals commit nothing.
- Guards: authority and content-version checks on open, `REQUIRE_EXISTING` mode so a missing store is never silently recreated, unknown schema/corrupt file refused and preserved, tampered rows preserved and block use (`STORED_DATA_INVALID`), stale profile/wallet revisions rejected, projection backlog (`projectionBacklog`/`markProjected`) for crash recovery, schema-zero `migrate` recording its operation ID and source digest (re-run is a no-op).
- Fault injection (`Faults`): crashes after validation, before commit and after commit are covered; reopening shows no change or a replayable committed result with no second debit or roll.

Verification: `:domain:test` 71 and `:store:test` 29 passing (100 total), `:fabric:build` successful; a mutation check (disabling replay) failed 11 store tests. No in-game verification.

Not done: wiring the store into `fabric` and replacing the prototype `PokemonProfiles`; the application service (ownership, battle/trade locks, preview tokens); SQLite native-library packaging inside the Fabric jar (jar-in-jar must be proven on a dedicated server); tables for acquisition intents, reward entitlements, encounter runs and pending presentations; consistent world+SQLite backup; catalyst threshold (100) is provisional.

## Fabric wiring and enemy generation — 2026-10-05

**Fabric wiring** (`fabric/`): the prototype's schema-0 `PokemonProfiles` was replaced by `AscendRuntime` (opens `<world>/cobbleascend/progression.db` plus an `authority.id` marker; a missing/mismatched/unreadable store disables progression instead of resetting it) and `AscendService` (acquire, reconcile, level catch-up, login sweep). Capture and hatch acquisitions use deterministic operation IDs, so repeated callbacks and restarts resolve the same profile. Schema-0 NBT is imported once and its source kept under `cobbleascend_schema0`; unreadable or foreign data is quarantined untouched. The Pokemon's NBT holds a schema-1 projection that is rewritten whenever it differs from the store. Level-ups (`LEVEL_UP_EVENT`, read on the next task) and every login (party + PC) award missed milestones. Commands: `/ascend status|inspect|wallet`, operator-only `/ascend admin initialize|grant`. There are no crafting or spending commands. The pre-wiring prototype jar is kept at `releases/CobbleAscend-0.1.0-prototype-schema0-capture.jar`.

Verification: `:fabric:build` compiles against Cobblemon 1.8.1; jar nests `domain`, `store` and `sqlite-jdbc` (checked by `tools/verify_artifact.py`); dev-runtime loader smoke shows `SQLite driver OK (engine 3.53.4)` under Fabric Knot and Showdown starting before the deliberate EULA stop. **Not verified:** a real world (store creation, capture, hatch, level-up, restart, PC/party, trade), the production nested jar-in-jar load of the SQLite native library, and `AscendService` itself (it needs a live server; its logic rests on the unit-tested store and domain).

**Enemy generation** (`domain/.../v1/`): `CombatSnapshot`, `EnemyTier`/`EnemyTiers` (`design/enemy-tiers.json`), `EnemySpec`, `EnemyGenerator` and `RankedProgression.rollInitialSlots`. See [ENEMY-SNAPSHOTS.md](ENEMY-SNAPSHOTS.md). Not connected to any battle; which enemies use it is undecided.

Verification: `:domain:test` 82 and `:store:test` 30 passing (112 total).

## Inspect screen design and wild ratings — 2026-10-05

- **Inspect screen preview:** `design/inspect/` (see its README). Layout approved, restyled with Cobblemon personality. Decisions: Mixin buttons on Cobblemon's battle overlay and summary header; scouting gates enemy rarity/modifiers (then also level, types, base stats, never IVs/EVs/moves); scouting sources are a CobbleTowers modifier, raid scouting, and a one-use **Scouter**. None of the native screen or Mixins exists yet.
- **Wild rating derived from the Pokemon's ID (decided):** `RankedProgression.rateWild` / `createWild` use HMAC-SHA256(server secret, catalog version, Pokemon UUID) to seed the rarity and slot draw, so a Scouter preview equals the capture result, fleeing cannot reroll it, and nothing is stored on the entity. The 32-byte secret lives in the store's `meta` table (created on open, never sent to clients). The capture path (`AscendService.acquire`) uses it for wild captures; hatch and admin acquisitions keep their own rules. `AscendService.previewWild` is the hook for scouting sources. **Unverified assumption:** a wild Pokemon keeps its UUID through capture (and battle clones do not interfere); this needs a live-world test before relying on it. A catalog version change deliberately changes ratings.
- **Scouter (decided 2026-10-05):** no recipe yet; obtainable only as a CobbleTowers reward. It is the wallet material `scouter` (account-bound, no physical item). One use reveals one chosen enemy for that encounter only; the reveal is in memory and ends with the encounter; unscouted enemies show the full "?" layout; the Scouter is spent only on a valid reveal (already-revealed or no Scouter costs nothing). Built in `store`: `ProgressionStore.spend`, `ScoutingService` (`grantScouters` for the Towers reward, `use`, `isRevealed`, `endEncounter`). Encounter IDs must never be reused. **Tower drops (provisional):** one roll per cleared floor, 5%, raised to 15% for that floor's rewards when the floor has the Keen Eye modifier; one Scouter per drop (`ScouterDrops`). No stack cap and no cooldown (a use is single-use; "16" only matters if a physical item is ever added). **Raid scouting (decided):** the reveal is SHARED with the whole raid party (`ScoutingService.Scope.SHARED`; the user's wallet pays, teammates pay nothing), usable in the lobby and in battle until the boss is defeated, and the boss's fixed Unique is HIDDEN until scouted (the reveal includes it). Raids get no Scouter drops; they only consume. Not built: the tower/raid callers, the in-game use button, the reveal UI.

## AscensionLib extraction — 2026-10-05

Decided with the owner: name AscensionLib; it holds everything including the Fabric events and `/ascend` commands (so CobbleRaids/CobbleTowers installs also carry capture rarity and the commands); one entry-point service.

- **Contents:** nests `domain`, `store` and `sqlite-jdbc` (Java packages stay `com.cobbleascend.domain|store`; renaming is mechanical and deferred). Package `com.ascensionlib`: `AscensionLib` (mod init; opens the world store on SERVER_STARTING, closes on SERVER_STOPPING, registers the wiring), `AscensionRuntime`, `ProfileService` (formerly `AscendRuntime`/`AscendService`), `AscendWiring` (Cobblemon capture/hatch/level events, login sweep and the `/ascend` commands; formerly `CobbleAscend`), and `AscensionApi`, the entry point: `service()`, `store()`, `scouting()`, `rules()`, `status()`. Everything is empty/disabled while no world runs or the store was refused; callers must never fall back to their own storage.
- **Kept for compatibility:** the data directory `<world>/cobbleascend/`, the Pokemon NBT keys `cobbleascend`/`cobbleascend_schema0` and the operation-ID prefix are unchanged, so existing worlds and recorded operations still resolve. Do not rename them without a migration. Log lines are now tagged `(ascensionlib)`.
- **Dev run:** `:ascensionlib:runServer`, run directory `ascensionlib/run/` (moved from `fabric/run/`, same world and authority).

Live dev run `verification/live-run-6.log` (no player): SQLite OK, the existing world store reopened with the same authority and no new store, `/ascend status` active. The caller (Raids/Towers) decides amounts; the library pays only on `VICTORY` (defeat/abort never pay), one store operation per `(encounterId, playerId, rewardKind)` with a derived operation ID, so a repeated callback or post-crash retry pays only those not yet paid. Facets only on bosses (50% on the first, 100% from floor 10), cores 7.5% per boss, Unique Fragments on every boss (1, plus a second 43% of the time: 1.43 average, so a 100-fragment Catalyst about every 35 runs to floor 10; owner ruling 2026-10-05, was 5% per boss), never Scouters or Catalysts. - No client GUI or reveal animation; capture notification is plain server chat.
- No canonical SQLite store, authority registry, duplicate-clone quarantine or production schema migration.
- No real crafting transactions, persistent wallets, research grants or encounter rewards.
- No hatch/legacy/import hooks beyond explicit Common operator initialization.
- No standalone Trial battles, progression unlocks or automatic attunement awards.
- No raid integration. Prior investigation is retained solely for later work.
- No full gameplay persistence/restart/capture/PC/trade/evolution verification or production-jar dedicated-world test.

Capture ownership confirmation waits up to 200 server ticks for a known pending capture; timeout creates no profile. This is a bounded pending-operation policy, not proof of event timing in every storage addon. On a server crash before queued assignment finishes, this prototype can leave that capture uninitialized. Durable acquisition reconciliation is part of the full store milestone. The prototype must not be represented as crash-safe production progression.

## Schema-zero boundary

The prototype's `persistentData.cobbleascend` is a JSON string containing schema 0, profile/native IDs, revision, rarity, initial rarity, attunement, origin and rolled affixes. This is intentionally simpler than `design/profile-example.json`, which illustrates planned production schema 1. A future migration must explicitly import validated schema-zero profiles into the canonical store and write the new projection. Never install a full-store build that silently treats these captures as fresh random rolls.

No deployed world was changed during development. The artifact is for controlled development-world testing. The next best task is the real capture/PC/restart acceptance matrix followed by a single simulator damage-affix spike; it is premature to expose currency spending before durable storage is implemented.
