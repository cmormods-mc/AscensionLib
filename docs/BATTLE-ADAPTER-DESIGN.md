# Battle adapter design (draft for approval, 2026-10-05)

Nothing here is built. This is the design the owner asked for before any code. It makes the 24 catalog affixes act in
battle. It follows the spec's section 3 and 7 rules: effects run **inside the Showdown simulator** with its own rounding,
immunities and failure paths; nothing invents HP changes in a second world-side listener; every value is frozen per battle.

## 1. What has to happen at battle start

Every battle goes through Cobblemon's `BattleRegistry.startShowdown`, which CobbleRaids already intercepts to add fields to the
`>start` payload's `format` object (`ShowdownExtensions.registerFormatFields`, called for **every** battle with the battle id and
the player ids). That is the single hook for all battle kinds, so wild PvE needs no extra entry point.

At that moment the lib:

1. **Classifies the battle** from its actors: two players = PvP, off (nothing sent). Otherwise it continues.
2. **Resolves each side's Pokemon to a frozen `CombatSnapshot`:**
   - a player's Pokemon: `CombatSnapshot.ofProfile` of its stored profile (no profile, no effects);
   - an encounter's enemy (tower opponent, raid or tower boss): the snapshot the encounter **declared** (the same one a Scouter
     reveals, generated by `EnemyGenerator`), so what was scouted is what fights;
   - a **wild Pokemon**: the snapshot of its **derived rating** (`RankedProgression.rateWild`: its own UUID, the server secret and
     the catalog version, plus its level's milestone ranks). This is the very rating a Scouter previews and a capture awards, so
     what you scout is what it fights with and what you catch. It is computed per battle and never stored. (This supersedes the
     earlier "wild stay native"; the owner wants random Pokemon to carry affixes.)
   - a trainer or NPC: **native for now**, no effects. Not decided; say so if they should carry affixes too.
3. **Sends one declarative payload**, `format.ascensionFx`, which a new Showdown module (`ascension-fx.js`) reads.

The enemy needs to be known *before* the battle exists, but the format fields are built *during* start. So an encounter owner
**arms** the lib first: `AscensionEncounters.armBattle(playerIds, encounterId)` just before it starts the battle and
`disarm(playerIds)` after, the same shape as Towers' `TowerBattleFx.armBossBattle`. A battle with no armed encounter has no enemy
effects. (New contract methods; the existing ones do not change.)

## 2. Where the simulator code lives (the owner's question)

**Yes, it can, and it is where this should end up.** CobbleRaids' Showdown integration splits cleanly into a generic host and a
raid-specific patch:

| Generic host (movable) | Raid-specific (stays in Raids) |
|---|---|
| `ShowdownExtensions` API, `ShowdownExtensionRegistry`, `ShowdownFormatExtras` (format fields) | `raid-patch.js` raid maths (shared pool, damage/heal instructions), `RaidDamageInstruction`, `RaidFieldInstruction`, `RaidPoolInstruction` |
| `ShowdownIntegrationInstaller` (unbundle copy, the second repair at `SERVER_STARTED`, structural edit of `index.js`), the two installer Mixins | `RaidBattleRegistryMixin`'s raid battle start |
| The tail of `raid-patch.js` that loads every `ext-*.js` | |

The cost is that today **Raids is the only installer and the lib is optional for it**. If the lib hosts the installer, then
every raid needs the lib (Raids would register its raid patch as just another module, like Towers does today). That is the
direction you described, but it changes Raids' install requirements, and that installer has already been through a hard race
with `mega_showdown` (it must stay exactly as robust: structural matching, two application points, fail closed for ascension
and open for battles).

**Recommendation: two steps, one decision now.**

1. **Now:** build the adapter against an internal `ShowdownHost` interface. First implementation reaches Raids' existing
   `ShowdownExtensions` by reflection. Nothing in Raids changes, so the effects can be proven in the real simulator without
   moving the installer at the same time. Without Raids installed the adapter says so once and effects stay off.
2. **Then, as its own project:** move the generic host into the lib and give `ShowdownHost` a second implementation. Raids and
   Towers then call the lib's API, and Raids' `ShowdownExtensions` becomes a thin forwarder for one release. This is a refactor
   with its own tests and its own live check on top of a working adapter, instead of being tangled into it.

The alternative (extract first) is possible but means every adapter bug could also be an installer bug.

## 3. The simulator module

`ascension-fx.js`, installed as `ext-ascensionlib.js`, follows the properties P23 already proved for `tower-fx.js`:

- **Does nothing unless asked.** It wraps only `Battle.prototype.start` and returns at once unless `battle.format.ascensionFx`
  exists; a battle without it is byte-for-byte unchanged (tested against a run with the module absent).
- **Declarative, bounded, isolated.** The payload is a list of named effects with validated parameters; no code, no `eval`.
  At most 12 Pokemon and 8 effects each. Unknown effect ids are ignored. One failing effect is logged into the battle and skipped.
- **Native maths.** Damage is changed by wrapping `modifyDamage` on **that battle's own `actions` instance**, using the
  simulator's own `battle.modify` so rounding stays native; immune and blocked hits are never touched (no forced minimum of 1).
- **Reads back.** It reports what it applied, not what it was asked.

### Which hook each affix needs

All 24 current affixes are damage or healing modifiers. None needs status attribution, so the burn/poison ledger of spec 8.2
is **not** part of this work.

| Channel | Affixes | Hook |
|---|---|---|
| Outgoing damage (12) | `type_focus`, `physical_force`, `special_force`, `healthy_force`, `last_stand`, `defiant_force`, `type_mastery`, `overwhelming_force`, `kindred_force`, `executioner`, `opening_strike`, `super_effective_force` | `modifyDamage`, user side. Conditions read the move (type, category), the user's HP and status before the move, the target's HP, native type effectiveness, "first damaging move after entering". |
| Incoming reduction (10) | `type_ward`, `healthy_guard`, `steadfast_guard`, `status_guard`, `opening_guard`, `iron_resolve`, `type_bulwark`, `resilient_hide`, `physical_bulwark`, `special_bulwark` | `modifyDamage`, target side. `opening_guard` needs a once-per-battle flag per holder. |
| Healing (2) | `restorative`, `triumphant` | A wrapper on the instance's `heal`, only when the heal comes from the holder's own move (drain or self-recovery), never items or abilities; `triumphant` also needs "this direct move fainted the target". |

Not yet specified by the catalog and **deferred**: Unique effects (Ashen Heart needs burn attribution), and the extra affixes in spec 8.1
(Smoldering, Venomous, Affliction Hunter, Siphoning, Relay Guard, Vengeful).

## 4. Identity: how a Pokemon in the simulator maps to a snapshot (settled by the spike)

The payload keys each effect list by the **uuid Cobblemon packs into the team**, not by side or slot, so nothing depends on actor
order, doubles or Raids' rewritten `p1..pN` ids. Verified (section 9):

- Cobblemon's packed team carries a uuid as its third field and the simulator keeps it as `pokemon.uuid`; effects keyed by it reach
  exactly that Pokemon and nothing else.
- The uuid packed is `BattlePokemon.effectedPokemon.uuid`. A raid or tower boss battle packs **clones** (`effectedPokemon`) of the
  party; `BattlePokemon.originalPokemon` is the real one. So the Java side resolves the **profile from `originalPokemon`** and
  keys the payload by the **`effectedPokemon` uuid**. It never has to know whether a Pokemon is a clone.
- The battle is already in `BattleRegistry` when the format fields are built (`startBattle` puts it in the map, then calls
  `startShowdown`), and the actors' Showdown ids are set, so `BattleRegistry.getBattle(battleId)` gives every actor and
  `BattlePokemon` at that moment.

## 5. Stacking, caps and order (decided: multiply each one)

Within a channel every active effect is its own multiplier, then the channel total is capped once:

- **Outgoing:** `Π (1 + pᵢ) − 1`, capped at 100%.
- **Incoming:** reduction `1 − Π (1 − rᵢ)`, capped at 50%.
- **Healing:** `Π (1 + hᵢ) − 1`, capped at 50%.

Because each value is small, the product is close to the sum; the difference only shows with several large affixes (a rank V
powerhouse plus others). The caps stay the ceilings in `balance.json`. Order of application inside one hit: outgoing multiplier
(user), then incoming reduction (target), each through `battle.modify`, after the simulator's own modifiers. Caps and values are
the frozen ones in the snapshot's catalog version, not re-read during the battle. **The spec still requires a balance pass on
per-channel caps and ordering at rank V before a live release**; these are the provisional rules for the build.

## 6. Failure policy

Fail closed for ascension, open for battles. No profile, an unreadable snapshot, a provider that throws, a module that fails to
load, a payload over the size limit: the battle starts with no effects and the log says why, once. The module never changes a
battle it was not asked about. PvP is never affected.

## 7. Verification

1. **Simulator harness (no server):** `validation/showdown/ascension_fx_test.js`, modelled on Towers' `tower_fx_test.js`, loads the
   real unbundled simulator and drives real battles with the same `>start` and `>player` lines. Per effect it asserts the damage
   or heal actually dealt with and without it (fixed seed), the cap, the condition both ways (HP thresholds, type, category,
   first move), immunity untouched, no-payload identity, and hostile payloads.
2. **Java unit tests:** classification, snapshot resolution, payload building, the multiplicative cap rule (pure, in `domain`).
3. **Live:** a wild battle, a tower floor and a raid boss with a known profile, comparing damage with and without effects.

## 9. Spike results (2026-10-05)

`validation/showdown/spike_ascension_fx.js` is a prototype module plus 17 tests run against the real unbundled simulator
(`node validation/showdown/spike_ascension_fx.js --showdown-dir <dir>`; no server, no player). **All 17 pass.** It proves:

| Question | Result |
|---|---|
| Identity by packed uuid | Effects reach exactly the keyed Pokemon; an unknown uuid does nothing. |
| `modifyDamage` wrap on the battle's own `actions` | +20% lands within native rounding of 1.2x; typed affixes apply to their type only; `super_effective_force` reads native effectiveness (`getMoveHitData(move).typeMod`, set by the engine before the wrapper sees the result), and an immune hit is never touched. |
| HP conditions | The wrapper runs before the damage is applied, so "HP before the move" is just `pokemon.hp`. |
| Stacking and caps | Product of the active multipliers, capped once: +100% outgoing, 50% incoming reduction. A reduction never takes a connecting hit below the engine's minimum of 1. |
| First-move and once-per-battle conditions | `pokemon.activeMoveActions` gives "first damaging move since entering" (`opening_strike`); a per-Pokemon flag gives `opening_guard`. |
| Healing | A heal-flag move (Recover, Roost) calls `pokemon.heal(amount)` directly with no source or effect, so the hook is a **per-Pokemon `heal` wrapper**, not `battle.heal`. The holder's own move is `battle.activePokemon === holder` with no effect, a Move effect, or the `drain` condition. Aqua Ring (a residual heal) and the **opponent's** drain are not boosted. |
| `triumphant` | A wrapper on `battle.faintMessages` reads `faintQueue` (target, source, effect) before the engine drains it, then heals the killer directly with a plain `-heal` line (no `[from]`, which Cobblemon's client would try to interpret). |
| Hostile or missing payload | A bad payload never stops a battle; no payload is byte-identical to a battle without the module. |

What the spike did **not** cover, still for slice 1:
- Running next to CobbleTowers' `tower-fx.js`, which also wraps `modifyDamage` on the same `actions` object. Wrappers chain, so it
  should compose, but it needs a test with both loaded.
- The Java side (nothing was built): resolving profiles and the wild rating, building the payload, the Raids extension hookup.
- Doubles and the raid's one-shared-side shape (keyed by uuid, so it should not matter, but it has not been run).
- Two Pokemon with the same uuid in one battle (a mirror raid of clones). Cobblemon may clone with a fresh uuid; if it does not,
  the effects of both would merge onto one key.

## 11. Built (slices 1-3, 2026-10-05)

**Library** (`ascensionlib`, `domain`):
- `domain/v1/BattleFx` (an effect list per snapshot, the compact `ascensionFx` payload with the caps, a hard size limit) and
  `BattleFxPlanner` (which Pokemon act from what, see section 1; pure, 9 tests).
- `battle/ShowdownHost` and `RaidsShowdownHost` (reflection on CobbleRaids' `ShowdownExtensions`, API version 1 checked),
  `BattleFxInstall`, and a **pre-launch entrypoint** `AscensionPreLaunch` (the module must be registered before Cobblemon builds
  its simulator).
- `battle/AscensionBattles.fieldsFor`: reads the battle from `BattleRegistry`, describes it to the planner, and returns the
  `ascensionFx` field. Fails closed (no effects, one log line) on any problem.
- `AscensionEncounters.armBattle(players, encounterId)` / `disarmBattle(players)` (a null or empty id arms the next battle as
  explicitly native). An armed encounter that was never declared also means native, so a failed declaration cannot turn a tower
  opponent into a randomly rated wild Pokemon.
- `ascension-fx.js` (all 24 catalog affixes: 12 outgoing, 10 incoming, 2 healing), and `validation/showdown/ascension_fx_test.js`
  (21 tests, including that every affix in `affixes.json` has a handler and that it composes with `tower-fx.js`).

**CobbleTowers:** every opponent and boss is now declared and armed **before** its battle starts (`AscensionLibScouting.armed`),
the boss through a `beforeStart` hook in `TowerBossAdapter` (its encounter id only exists inside `start`), and an Echo duel is
armed as explicitly native.

**Verified:** the harness passes 21 of 21 against both the test server's simulator and the dev server's own unbundled copy; a
headless dev server with CobbleRaids installed prints "Registered the Showdown module" and "[CobbleRaids] Showdown extension
ascensionlib-fx loaded", and the installed `ext-ascensionlib-fx.js` is byte-identical to the source
(`verification/live-run-8.log`).

**Not verified:** any real battle with a player. Whether the format field reaches the simulator and the effects land in a live
wild, tower or raid battle is exactly the live check of section 7.3. Raids does not arm its own raid bosses yet, so a raid boss
is native there. Without CobbleRaids installed the lib says so at launch and effects stay off.
